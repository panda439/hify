# Phase 16 · 让模型知道自己证据的边界（009）验收报告

**规格**：[specs/009-evidence-boundary-awareness/](../specs/009-evidence-boundary-awareness/) ｜ **日期**：2026-09-05

> ⚠️ **本报告的结论全部是机制证明。** 能证明的是"信号确实到了模型面前、只出现在该出现的
> 地方、字符计进了预算"；**不能**证明"回答变好了"。**"模型会因此答得更好"是假设，不是结论。**
> 本仓库没有可信的答案质量度量：`make eval` 带 LLM 裁判、同一份代码跑两次都不一致
> （宪法禁止拿它当证据），确定性门禁只覆盖检索与上下文组装，**不覆盖回答**。

---

## 1. 问题的实测形态

改动前，把六个场景跑过 `assembleContext` 并记录送给模型的完整消息序列，得到一个结论：

> **「检索了但没匹配」「压根没绑知识库」「检索失败降级」「多轮空检索」——
> 四种情况送给模型的消息序列逐字节相同**，而且内容里连"知识库"三个字都没有。

```
[user]      历史消息内容
[assistant] 历史消息内容
[user]      用户的最新问题
```

模型于是按参数知识作答，语气与有依据时毫无区别。用户把合同传进知识库、问了合同里的问题、
拿到一个听起来很有把握实际上零依据的回答，而**他没有任何线索去怀疑这一点**。

## 2. 改了什么

| # | 改动 | 落点 |
|---|---|---|
| 1 | 检索执行且无匹配时，注入一句事实陈述 | `context.go` |
| 2 | 命中文档不完整时，在 `<retrieved_sources>` 内加一条按文档去重的汇总 | `context.go` |
| 3 | 批量查询文档缺失情况（**一次往返**，不按文档循环） | `knowledge` 的 `DocumentCoverages` |
| 4 | 新增字符计进 `computeFixedBudget` | `context.go` |
| 5 | ⭐ **新增上下文组装确定性门禁** `make eval-context-gate` | `context_gate_test.go` |

注入的实际内容：

```
[system] 本轮已检索知识库，未匹配到任何相关内容。

<incomplete_documents>
合同.pdf：5 页未提取文本、1 页无法解析
</incomplete_documents>
```

⛔ **两处都不含行为指令**——没有"请谨慎回答"、没有"请说明你不确定"。给指令等于**主动诱导
对冲**，而过度对冲正是本期最担心的副作用，且本仓库**没有能力发现它已经发生**。
陈述事实，把判断留给模型。这不是保证，是把风险压到可控范围的唯一手段。

## 4. ⭐ 门禁当场抓到一个自欺的测试场景

门禁第一次比对时报告 `evidence_present_incomplete_docs` **改动前后逐字节没变**——而它本该变。

原因不是实现坏了（专门的验收用例是过的），是**这个门禁场景自己在骗自己**：夹具里文档
被**起名叫** `doc-incomplete`，却从没配过缺页数据，于是它实际测的是"完整文档"，
与场景 1 完全重复。

**如果没有这条门禁，这个场景会以一个自欺的形态长期绿着**，而且名字看起来完全正当。
这是"回归基线 + 预期改变"两类场景分开标注的直接收益：**一个本该变却没变的场景，
和一个本该不变却变了的场景，同样是失败**。

## 5. 一条既有断言被迫重写（值得记）

`TestIntegrationAssembleContextAllCandidatesBelowThresholdChargesNothingForRAG` 原本断言
"共 4 条消息"，用来防**幽灵预留**——候选被分数全部过滤、证据为空时，绝不能仍按 RAG 全额
预留预算把历史白白挤掉。

009 之后这里**确实多了一条消息**：候选被过滤光 = 检索跑了、没匹配到可用内容，正是空检索
信号该出现的场合。断言因此从"消息条数"改成它**真正要防的那件事**：只为信号那一句话付费、
不为不存在的 RAG 全额付费；并额外断言历史不被过度挤占。

⚠️ 注释里写明了**不许把它改成宽松的"条数 >= 4"**——那样幽灵预留回来了也不会被发现，
而那正是这条用例存在的全部理由。

## 6. 已知边界（不得包装）

### 6.1 ⚠️ "过度声明不确定"这个风险没有度量，只有缓解

模型拿到这些信号后，可能对**本来答得很好**的问题也开始加免责声明。本仓库测不了这件事。
缓解手段只有一个：注入文本**只陈述事实、不给行为指令**（§2）。
**不得写成"已验证无副作用"** —— 正确的说法是"已把注入面压到最小，且无法度量"。

### 6.2 检索失败与没绑知识库对模型不可区分

两者都不注入。这是知情取舍：两种情况下我们手里都**没有为真的话可说**——
把基础设施故障说成"知识库里没有该内容"是拿故障冒充结论，而把故障本身告诉模型
又会让它讲给用户听。**沉默好过说一句不确定为真的话。**

### 6.3 新门禁只覆盖 `assembleContext` 的产出，不覆盖模型的回答

它证明"送出去的东西正是我们打算送的"，**不证明**"送出去之后效果更好"。
门禁绿了不等于效果好。

### 6.4 模型仍可能滥用这些信号

FR-012 要求"不完整不是拒答的理由"，但那条约束**写在提示词里就意味着它是尽力而为**，
不是保证。本期没有、也无法验证它。

---

## 7. 这条门禁的价值超出本期

上下文组装是整条对话链路上**最容易被无声改坏的地方**：改错了不报错、不会有任何测试变红，
只会让回答慢慢变差——而没有人会把"最近答得不太好"和三周前某次改提示词的提交联系起来。

`make eval-context-gate` 是本期唯一**新增的可度量能力**，而不只是一个新功能。
将来任何人动提示词、动预算、动组装顺序，都会在这里响一声。
