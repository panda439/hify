# Hify RAG Phase 8：检索证据准入设计

日期：2026-08-08

## 1. 背景与目标

Hify 已完成结构感知分块、Hybrid Search、邻接窗口、精确内容去重、确定性检索门禁和邻接批量查询。当前 `knowledge.Service.Retrieve` 会返回排序最靠前的候选，`conversation.selectEvidence` 再通过统一的 `ragMinSimilarityScore=0.2` 过滤低分项。

这个边界存在两个问题：

1. 向量余弦相似度与 `pg_trgm` 关键词相似度不是同一种量尺，统一阈值不能准确表达两路召回的可信条件。
2. 低质量候选在对话层被过滤前，已经占用核心 topK 并触发邻接查询，可能挤掉后面的合格候选并产生无意义数据库工作。

Phase 8 的目标是增加一个确定性的“证据准入层”：只有召回信号足够明确的候选才能成为核心块。问题与非空知识库完全无关时，`Retrieve` 返回空结果；对话仍正常调用模型，但不注入知识库资料、不生成知识库引用。

本阶段采取保守策略：相关性不确定时宁可少召回，也不把可能无关的资料注入模型。

## 2. 方案选择

### 2.1 不采用：直接提高统一分数线

只提高 `ragMinSimilarityScore` 改动最小，但混淆向量分数和关键词分数，且过滤发生得太晚，无法让后续合格候选补位，也无法避免低质量候选触发邻接查询。

### 2.2 不采用：动态相对分差

按第一名与后续候选的分差判断，可以适应部分查询分布；但当整批结果都很差时，第一名仍然是“相对最好”，不能证明它真实相关，不符合本阶段保守目标。

### 2.3 采用：按召回来源设置绝对准入门槛

RRF 继续负责排序，准入层使用向量、关键词各自的原始相关度信号判断候选是否有资格成为核心块：

- 向量相似度 `>= 0.35`，候选通过；
- 关键词相似度 `>= 0.45`，候选通过；
- 同时被两路召回时，任意一路达标即可通过；
- 两路都未达标则拒绝。

门槛是包内常量，不增加运行时配置。本阶段用固定真实数据库数据校准并锁定行为；未来只有真实评测证据表明门槛不合适时，才单独立项调整。

## 3. 数据流与排序边界

处理顺序必须固定为：

1. 向量、关键词两路各自召回扩大候选集；
2. 按 chunk ID 汇总 RRF 信号；
3. 按现有规则完成确定性排序；
4. 在完整有界候选集上执行来源感知的证据准入；
5. 对通过准入的候选执行精确内容去重；
6. 截断到 topK，允许后面的合格候选补位；
7. 只为通过准入的核心块批量查询邻接块；
8. 按现有两层布局组装核心块与邻接块，再执行第二次内容去重。

准入不能放在 topK 截断后，否则被拒绝的候选会留下空槽，后面的合格候选无法补位。准入也不能放在邻接查询后，否则低质量核心块仍会产生无意义查询。

准入必须发生在精确内容去重之前。若正文相同的 A、B 中，A 的 RRF 排名更高但两路原始分数均未达标，B 排名稍低但有一路达标，先去重会错误地保留 A、删除 B，随后 A 又被准入层删除，导致合格的 B 永久丢失。正确顺序是先删除不合格的 A，再在剩余合格候选中执行“同正文保留排名最高者”。

RRF 的融合排名公式、`vectorWeight`、`keywordWeight`、`rrfK` 和三级确定性排序均不改变。

## 4. 信号模型

RRF 内部的每个 `fusionEntry` 需要保留：

- 是否被向量路径命中；
- 该 chunk 的最高向量相似度；
- 是否被关键词路径命中；
- 该 chunk 的最高关键词相似度。

这些字段只服务于 `internal/knowledge` 的准入判断，不进入公开 API、Citation、SSE 或持久化模型。最终 `RetrievedChunk.Score` 继续保持现有语义：向量、关键词两路相关度中的较大值；邻接块继续继承所属核心块的 Score。

不能用 RRF fusionScore 做准入判断。fusionScore 是排名信号，不是 0..1 的相关度，也不能与准入门槛直接比较。

## 5. 无相关证据时的行为

当所有候选都未通过准入：

- `knowledge.Service.Retrieve` 返回空切片和 nil error；
- 不执行邻接批量查询；
- `conversation.assembleContext` 不生成 `<retrieved_sources>` 消息；
- 不添加 citation system rules；
- 不生成知识库 Citation；
- 对话仍正常调用模型回答。

本阶段不做“知识库无答案”固定回复，也不阻止模型基于自身知识回答。

## 6. 可观测性与隐私

增加安全计数，用于区分召回与准入效果：

- `candidate_count_before_admission`；
- `filtered_by_vector_admission_count`；
- `filtered_by_keyword_admission_count`；
- `filtered_by_all_admission_count`；
- `admitted_anchor_count`。

具体计数口径在实现计划中应避免重复计算：一个候选最终只能计入一个“被全部准入规则拒绝”的总数；按路径计数用于说明该路径未达标，不应与总数混为同一指标。

日志与 Trace 只允许记录计数、阈值常量和模型/知识库等既有非正文标识；禁止记录 query、chunk 正文、embedding、内容 fingerprint 或完整候选分数列表。

## 7. 失败与兼容性

准入判断是纯内存确定性逻辑，不引入新的外部失败点。向量或关键词一路失败时，沿用当前 best-effort 行为：

- 向量失败、关键词成功：只用关键词信号判断；
- 关键词失败、向量成功：只用向量信号判断；
- 两路都失败或所有结果不达标：返回空；
- context 取消/超时继续按现有规则传播。

公开 `knowledge.Service` 接口、Citation 协议、前端、RAG 字符预算和数据库 schema 不改变。

`conversation.selectEvidence` 的 0.2 分数线暂时保留，作为下游防御性保护，不把它删除或提高。本阶段的主要准入发生在 knowledge 层；两层保护的语义应在文档中写清楚，避免未来误认为重复代码。

## 8. 测试与验收

### 8.1 纯逻辑测试

- 向量分数等于、高于、低于 0.35；
- 关键词分数等于、高于、低于 0.45；
- 双路命中时只有一路达标；
- 两路都不达标；
- 缺少某一路信号时不能把零值误当真实分数；
- `A(拒绝)、B(通过)、C(通过) + topK=2` 返回 `B、C`；
- 精确内容相同的高排名拒绝项与低排名通过项并存时，先拒绝前者，再保留后者；两个都通过时仍保留排名更高者，且保留项字段不被改写。

### 8.2 编排测试

- 所有核心候选被拒绝时，邻接 batch spy 调用次数为 0；
- 只有通过准入的核心块进入邻接请求集合；
- 普通邻接错误降级和 context 错误传播不回归。

### 8.3 真实数据库测试

- 非空知识库、完全无关查询最终返回空；
- 强向量命中通过；
- 强关键词命中通过；
- 双路弱信号均不达标时拒绝；
- topK 前部存在拒绝项时，后续合格候选补位；
- 被拒绝候选不会触发邻接查询；
- 跨知识库、跨 embedding 模型场景保持全局排序与准入正确。

### 8.4 Phase 6 门禁扩展

原有 6 个 case 必须继续全部通过，并新增至少 3 个负向/边界 case：

1. 非空知识库 + 无关查询：返回空；
2. 仅低于门槛的向量候选：返回空；
3. 低分候选排在前面、后续合格候选存在：合格候选补位。

门禁仍不依赖真实 LLM/Judge，全部数据库 case 必须真实执行，不得静默 skip。

## 9. 禁止范围

- 不新增 LLM Reranker、Cross Encoder、Query Rewrite、Multi Query 或 HyDE；
- 不修改 RRF 权重、`candidateK`、topK、邻接窗口大小或批量查询架构；
- 不增加动态阈值配置；
- 不修改 Citation、SSE 对外协议或前端；
- 不提高 RAG 预算；
- 不用相对排名代替绝对准入条件；
- 不把真实 query、正文或 embedding 写入报告与日志。

## 10. 完成标准

- 无关问题不会向模型注入知识库内容；
- 保守准入不会阻止明确的向量或关键词命中；
- 过滤在 topK 与邻接查询之前完成，合格候选能够补位；
- Phase 3-7 现有排序、去重、邻接和门禁行为不回归；
- `make eval-retrieval-gate` 所有 case 真实执行并通过；
- `go test -count=1 ./...`、`go test -race -count=1 ./...`、`go vet ./...`、`make check-deps`、`git diff --check` 全部通过。
