# Feature Specification: RAG 查询优化与结果重排序

**Feature Branch**: `001-rag-query-rerank`

**Created**: 2026-08-24

**Status**: Draft

**Input**: User description: "RAG 检索链路增加「查询优化」与「重排序（Rerank）」两个能力。当前 knowledge.Service.Retrieve 直接拿用户原始 query 做向量+关键词双路召回、RRF 融合、来源感知准入、内容去重、topK 截断、邻接扩展。两个已知问题：(1) 多轮对话里用户的话常常是省略指代的短句（"那它的限制呢"），原始 query 直接检索召回质量差；口语化提问与文档书面表达词面不匹配，关键词路几乎打不中。(2) RRF 只是排名融合，不理解 query 与 chunk 的真实语义相关度，topK 内的顺序不可靠，最相关的证据可能排在后面被预算截断掉。目标：在召回前增加查询优化（改写/扩展成更适合检索的查询），在候选集截断到 topK 前增加重排序，用交叉编码器式的相关度打分重排候选。参考 research-agent 项目里已有的 query rewriter 做法。约束：必须可关闭、必须有失败降级（优化或重排失败时退回当前行为，不能让对话失败）、必须保持确定性可测、不破坏现有 RetrievedChunk.Score 语义与 Citation 协议。"

## Clarifications

### Session 2026-08-24

- Q: 重排序的相关度打分从哪来？ → **A: 新增 rerank 模型能力**——供应商模型体系增加第三类能力
  `rerank`，走 `/v1/rerank` 兼容接口（bge-reranker / Cohere / Jina 这类交叉编码器）。
  这意味着本次范围包含 migration 与 provider 模块改动。
- Q: 查询优化放在哪一层？ → **A: conversation 层**——在调用检索之前完成问题补全，
  再把补全后的问题作为检索输入传下去。`knowledge` 的对外契约不变。
- Q: 两个能力的开关配置在哪一级？ → **A: 全局配置**——进程级配置项（开关、模型、超时），
  不做每个 Agent 可配，前端不新增界面。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 多轮追问也能检索到正确资料 (Priority: P1)

用户在一个已绑定知识库的对话里连续提问。第一轮问「Hify 的分块策略是什么」，第二轮只说「那它的上限呢」。
今天第二轮几乎检索不到任何有用资料——这句话里没有任何实词能对上文档，向量表示也没有主语。
本功能要求系统在检索之前，先把这句依赖上下文的话补全成一个脱离聊天记录也能独立理解的检索问题
（例如「Hify 文档分块策略的分块大小上限是多少」），再拿补全后的问题去召回。

**Why this priority**: 这是多轮对话产品里最高频的失败形态，且完全发生在用户看不见的地方——
用户只会看到"助手第二轮突然不知道了"。修好它对回答质量的提升最大。

**Independent Test**: 单独实现查询优化、不做重排序，即可验证：构造一段两轮对话，第二轮用省略指代的短句提问，
断言系统实际用于检索的问题已被补全，且返回的证据与第一轮主题一致。

**Acceptance Scenarios**:

1. **Given** 上一轮已明确讨论「文档分块策略」，**When** 用户这一轮只说「那它的上限呢」，
   **Then** 系统用补全后的独立问题执行检索，并返回与分块策略上限相关的证据。
2. **Given** 用户这一轮的问题本身已经完整（含明确主语、无指代词），
   **When** 执行检索，**Then** 系统不改写该问题、不额外消耗模型调用，行为与本功能上线前完全一致。
3. **Given** 上文中存在两个都可能被「它」指代的对象，**When** 用户说「它怎么配置」，
   **Then** 系统不得凭猜测补全成其中之一；此时保持原问题检索，并照常回答（不打断对话去追问）。
4. **Given** 查询优化被关闭，**When** 用户提出任何问题，**Then** 系统直接用原始问题检索，
   行为与本功能上线前逐字一致。

---

### User Story 2 - 最相关的证据排在最前面 (Priority: P1)

同一个问题往往能召回一二十个"看起来沾边"的片段，但真正回答问题的只有一两个。
今天决定顺序的是两路召回的排名融合，它不理解问题和片段之间的真实语义关系，
真正的答案片段可能排在第 6 位，被 topK 截断或被上下文预算挤掉。
本功能要求在把候选截断到 topK 之前，按"这个片段对这个问题有多相关"重新排序。

**Why this priority**: 与 US1 同为 P1：US1 解决"召回不到"，US2 解决"召回到了但没用上"。
两者各自独立可用，合起来才覆盖检索质量的两类失败。

**Independent Test**: 单独实现重排序、不做查询优化，即可验证：构造一组候选，其中真正相关的片段在融合排名中位置靠后，
断言重排序后它进入 topK 且排在前列。

**Acceptance Scenarios**:

1. **Given** 一次检索产生了超过 topK 个候选，且真正相关的片段在融合排名中排在 topK 之外，
   **When** 执行重排序，**Then** 该片段进入最终结果并排在更靠前的位置。
2. **Given** 重排序完成，**When** 对话层按相关度阈值与上下文预算筛选证据，
   **Then** 每个片段对外暴露的相关度分数语义不变，引用编号与引用协议不变。
3. **Given** 两个片段在重排序中得到完全相同的分数，**When** 重复执行同一次检索，
   **Then** 两次结果的顺序完全一致（不依赖任何未固定的随机因素）。
4. **Given** 重排序被关闭，**When** 执行检索，**Then** 结果顺序与本功能上线前逐字一致。

---

### User Story 3 - 出问题时对话不受影响，且能看清发生了什么 (Priority: P2)

查询优化和重排序都依赖外部模型服务，它们会超时、会限流、会返回不可解析的内容。
运维者需要保证：这两个环节的任何失败都只让检索退回到今天的行为，绝不让用户的这一轮对话失败；
同时需要能从日志/追踪里看出这一轮到底有没有改写、有没有重排、失败了没有、多花了多少时间。

**Why this priority**: 不影响核心检索价值，但决定了这两个能力敢不敢在生产开着。

**Independent Test**: 让外部模型调用强制失败或超时，断言这一轮仍返回结果、仍正常回答，
且记录里出现明确的降级标记。

**Acceptance Scenarios**:

1. **Given** 查询优化所依赖的模型调用失败或超时，**When** 执行检索，
   **Then** 系统用原始问题继续检索，本轮对话正常完成，并记录一次降级。
2. **Given** 重排序所依赖的模型调用失败或超时，**When** 执行检索，
   **Then** 系统保留融合排名的原顺序继续后续流程，本轮对话正常完成，并记录一次降级。
3. **Given** 重排序返回的结果里包含系统没有送进去的片段标识、或缺失了部分片段，
   **When** 处理该返回，**Then** 系统视为不可信并整体降级为原顺序，不得部分采用。
4. **Given** 一轮检索完成，**When** 查看该轮的追踪记录，**Then** 能看到是否改写、是否重排、
   各自耗时与是否降级，且记录中不包含问题原文、片段正文或任何可还原它们的内容。

---

### Edge Cases

- 用户问题为空、或只有标点/表情时：不触发查询优化，按现有空查询逻辑处理。
- 用户问题极长（远超正常提问长度）时：不因为改写而让检索输入进一步膨胀，必须有明确上限。
- 对话的第一轮（没有任何历史）且问题不含指代词时：不触发改写，不产生额外模型调用与延迟。
- 召回候选为空、或全部被来源感知准入拒绝时：不执行重排序，不产生任何外部模型调用。
- 候选数量只有 1 个时：重排序不改变结果，且不应付出完整重排代价。
- 用户历史消息中包含"忽略以上指令"这类内容时：历史只能作为待分析数据参与问题补全，
  绝不能成为改变系统行为的指令。
- 改写结果为空字符串、与原问题无关、或明显超长时：视为不可信，退回原问题。
- 同一轮里查询优化与重排序同时失败：等价于本功能整体未启用，结果与上线前一致。

## Requirements *(mandatory)*

### Functional Requirements

**查询优化**

- **FR-001**: 系统 MUST 在执行召回之前，将用户当前问题与最近若干轮对话结合，产出一个"脱离聊天记录也能独立理解"的检索问题。
- **FR-002**: 系统 MUST 仅使用对话中已经明确出现过的信息进行补全，MUST NOT 引入用户没有表达过的目标、限制或范围。
- **FR-003**: 当指代对象存在多个合理候选、或缺少关键上下文时，系统 MUST NOT 猜测补全，MUST 退回使用原问题继续检索，并且 MUST NOT 中断本轮回答去向用户追问。
- **FR-004**: 当问题本身已完整、且没有可用历史时，系统 MUST 走"原样通过"的快速路径，MUST NOT 产生额外的外部模型调用。
- **FR-004a**（对 FR-004 的收紧，实现后补）: 当问题本身已完整时，系统 MUST 走快速路径，**无论是否存在历史**。最初实现里"有历史"就无条件触发改写，等于多轮对话每一轮都付一次外部模型调用；而改写要补的是指代，问题自足时没有任何东西可补。"已完整"的判定为：不含指代词，且去标点后长度与内容信号数均达标（阈值见 `queryrewrite.go`，需用 eval 集校准）。这是 FR-004 的超集，不与其冲突。
- **FR-005**: 系统 MUST 对改写结果做可信性校验（非空、长度上限、与原问题的最小相关性），校验不通过 MUST 退回原问题。
- **FR-006**: 对话历史与用户问题在参与改写时 MUST 被当作数据处理，MUST NOT 被解释为指令。

**重排序**

- **FR-007**: 系统 MUST 在候选集截断到 topK 之前、在来源感知准入与内容去重之后，对候选执行基于问题—片段相关度的重排序。
- **FR-008**: 重排序 MUST NOT 覆盖或改写片段对外暴露的相关度分数（该分数现有语义为两路召回相关度的较大值），重排分数只用于决定顺序。
- **FR-009**: 重排序 MUST 是确定性的：分数相同时 MUST 有稳定的最终排序依据，重复执行同一输入 MUST 得到逐字相同的顺序。
- **FR-010**: 重排序 MUST 在候选数为 0 或 1 时短路，不产生外部调用。
- **FR-011**: 重排序结果 MUST 与送入的候选集合完全对应；出现未知标识、重复标识或缺失标识时 MUST 整体丢弃该结果并退回原顺序。
- **FR-012**: 邻接块扩展 MUST 在重排序与 topK 截断之后执行，MUST NOT 为被重排淘汰的候选查询邻接块。

**开关、降级与可观测**

- **FR-013**: 查询优化与重排序 MUST 各自可独立开关，且默认状态 MUST 可配置。
- **FR-014**: 两个能力的任何失败（超时、限流、返回不可解析）MUST 降级为本功能上线前的行为，MUST NOT 使本轮对话失败。
- **FR-015**: 每个能力 MUST 有明确的超时上限，超时后 MUST 立即降级，MUST NOT 无限期占用本轮对话的响应时间。
- **FR-016**: 系统 MUST 记录每轮的能力开关状态、是否实际执行、是否降级、各自耗时与候选数量变化。
- **FR-017**: 上述记录 MUST NOT 包含用户问题原文、片段正文，或任何可还原它们的内容（如指纹、逐条分数明细）。
- **FR-018**: 两个能力关闭时，检索链路的输出 MUST 与本功能上线前逐字一致（可用固定输入回归验证）。

### Key Entities

- **检索问题（Search Query）**：真正送去召回的问题文本。来源可能是用户原问题，也可能是改写后的独立问题。
  与"用户原问题"是两个概念，后者始终是回答阶段呈现给模型的那一句。
- **候选片段（Candidate Chunk）**：已有概念。本功能新增一个只在检索链路内部存在的"重排相关度"，
  它不进入对外契约、不落库、不进入引用协议。
- **检索诊断（Retrieval Diagnostics）**：一轮检索的可观测汇总——是否改写、是否重排、是否降级、耗时、
  各阶段候选数量。只含计数与状态，不含内容。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在确定性检索门禁的受控数据集中，针对"依赖上文的省略式追问"场景，
  存在至少一组用例满足：改写关闭时检索不到目标片段、改写打开时检索到，且该行为可重复复现。
- **SC-002**: 在确定性检索门禁的受控数据集中，存在至少一组用例满足：
  目标片段在融合排名中位于 topK 之外、重排打开后进入 topK 且排名提升，且该行为可重复复现。

  > **度量方式修正（2026-08-24，重要）**：SC-001/SC-002 原写作"在固定回归测试集（`make eval`）中
  > 相对基线提升 30 / 15 个百分点"。实测证明这在本项目的环境里**无法度量**，原因有三层，
  > 每一层都足以让指标失效：
  >
  > 1. **语料规模**：评测知识库只有 4 个 chunk、2 篇文档，而 `retrievalTopK = 5`——
  >    每次检索都把整个语料全量返回，Hit@1 与 MRR 在结构上恒为 1.00，不存在可提升的余量。
  > 2. **嵌入是 mock**：知识库挂的是 `mock-embedding-model`（本地 mock server，32 维）。
  >    实测库内向量两两余弦在 0.78–0.94 之间，且语义相近的片段（两篇文档中都讲密码重置的段落，
  >    0.8515）反而低于毫不相干的片段（0.9352）。向量分不携带任何语义信息。
  > 3. **关键词路曾经是死的**：开发库的 PostgreSQL 迁移停在 version 3，`pg_trgm` 从未安装，
  >    关键词检索每次调用都失败降级为纯向量（已于 2026-08-24 修复至 version 4）。
  >
  > 扩充语料无法解决第 2 层——在非语义向量上放大语料只会让检索退化为随机。接入真实嵌入/重排
  > 模型可以解决，但需要付费 API，**仓库所有者明确决定不为学习项目承担这项成本**。
  >
  > 因此改为用 Phase 6 建立的确定性检索门禁度量：受控 seed 的向量 + 真实 pg_trgm + 隔离数据集，
  > 零成本、完全可复现、可进 `go test` 当回归门禁。
  >
  > **必须如实承认的边界**：这样度量证明的是**机制成立**（"改写确实改变了检索结果、重排确实改变了
  > 顺序"），**不是真实世界的效果幅度**。任何对外材料都不得把门禁通过表述成"在真实语料上提升了
  > N 个百分点"。若将来接入真实嵌入与重排模型，应另立任务重新度量真实效果。
- **SC-003**: 两个能力全部关闭时，**确定性检索门禁**（不含 LLM 与裁判，见下方说明）的输出与当前基线
  逐字节一致。

  > 验证方法修正（2026-08-24）：本条原写作"固定回归测试集（`make eval`）与基线 100% 一致"，
  > 这是不可能达成的——`make eval` 每条用例都要调用真实对话模型和裁判模型，两次跑同一份代码
  > 都不会得到相同输出。能对"逐字一致"给出真实证据的是 Phase 6 建立的确定性检索门禁
  > （真实 MySQL + pgvector + fake embedding，无 LLM、无裁判）。`make eval` 仍然有用，
  > 但它度量的是 SC-001/SC-002 这类**相对提升**，不能用来证明"零变化"。
- **SC-004**: 外部模型调用失败或超时的注入测试中，100% 的对话轮次仍能正常完成回答。
- **SC-005**: 单轮对话中，两个能力叠加引入的额外等待时间在 95% 的情况下不超过 2 秒；
  任一能力超过其超时上限时立即降级，不叠加等待。
- **SC-006**: 完整问题、无历史的单轮提问中，至少 90% 不触发查询优化的外部调用（快速路径命中率）。
- **SC-007**: 同一输入重复执行 20 次，最终结果顺序 100% 一致。

## Assumptions

- 已有的固定评测集（`eval/`）可以扩充"多轮省略式追问"用例，作为 SC-001/SC-002 的度量基准；
  基线取本功能上线前的一次完整评测结果。
- 现有的相关度下限（对话层的 0.2 分数线）与上下文预算策略保持不变，本功能不调整这些阈值。
- 现有的来源感知准入门槛（向量 0.35 / 关键词 0.45）保持不变，重排序不替代准入。
- 供应商体系当前只区分"对话"与"向量"两类模型能力；本次按 Clarifications 的决议引入第三类 `rerank` 能力，
  因此本功能范围包含一次 migration 与 provider 模块改动。
- 查询优化最多参考最近若干轮对话（默认 4 轮左右），不引入长期记忆。
- 前端不新增界面：两个能力的开关属于服务端配置，不在本次范围内暴露成用户可见设置。

## Out of Scope

- 语义级/模糊去重（当前只做规范化后完全相同内容去重，本次不变）。
- 引用协议、SSE 事件协议、前端展示的任何变更。
- 多查询扩展后的多路并行召回（本次只产出单条检索问题；多查询扩展列为后续可选增强）。
- 长期记忆、用户画像参与查询改写。
- 分块策略、嵌入模型、向量库的任何调整。
