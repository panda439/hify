# Feature Specification: 工具调用循环止损（Tool Loop Guard）

**Feature Branch**: `005-tool-loop-guard`

**Created**: 2026-09-02

**Status**: Draft

**Input**: `internal/conversation` 的工具调用循环目前只有一道防线——
`maxToolCallIterations = 5` 的硬计数器，触顶直接发 `EventError` 终止本轮。

> **起草时的一处事实更正**：初稿写的是「连已生成的中间内容都不保存」，核对代码后确认**是错的**。
> 循环里每一轮迭代都已落库——助手消息（含 `tool_calls`）由 `persistAssistantTurn` 持久化，
> 工具结果由 `runToolCall` 以 `role=tool` 持久化。
> **真实缺口更窄：内容都在，缺的是一个收尾的答复。**
> 用户拿到的是一条错误事件，会话历史里留下一串工具调用轮次却没有最终回复。
完整的止损应该是三层（见 `docs/rag-study-guide.md` §9.5），本期补第 2、3 层。

## Clarifications

### Session 2026-09-02

- Q: 第三层「触顶降级」要不要多调一次模型让它带保留地作答？
  → **A: 不再调模型**。触顶时**补一条程序拼接的收尾助手消息**并以正常结束事件收尾，
  而不是发 `EventError`。（内容持久化本来就有，见上方事实更正——本期要补的只是「收尾」。）
  理由：触顶本身已经是异常路径，再多打一次模型有两个代价——一是喂部分结果让模型作答会诱发
  **填空式幻觉**（它会把缺的那部分编出来），二是多一次调用与延迟。
  本期先拿走「纯体验收益、零额外模型调用」的那部分。
  **「让模型基于中间结果作答」不在本期范围**，需要独立评估幻觉风险后单独立项。
- Q: 循环检测判定「相同调用」的粒度？ → **A: 工具名 + 参数 JSON 规范化后的哈希**。
  规范化只做**结构级**（对象 key 递归排序后紧凑序列化），**不做语义级**
  （不处理 `{"city":"北京"}` 与 `{"city":"Beijing"}` 这类等价）。
  理由：模型转圈时的重复调用**往往逐字相同**，结构级规范化足以覆盖绝大多数真实死循环；
  语义级去重会引入「什么算等价」的无穷判断，且有误杀合法重试的风险。
- Q: 检测到重复之后怎么办？ → **A: 注入一条系统消息给模型一条出路，并在本轮禁用该工具**。
  只注入消息不够——已知失败模式是**模型道歉之后再调一次同样的**。
  必须配合硬手段：把该工具从后续迭代的 tool 列表里摘掉。
- Q: 阈值是多少？ → **A: 同一调用连续出现第 3 次时触发**。
  取 3 而不是 2：合法的重试（工具本身瞬时失败后重试一次）应当被放过；
  连续第 3 次相同调用几乎不可能是有意的。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 模型卡在同一个调用上时能自己脱困 (Priority: P1)

模型拿相同参数反复调同一个工具，每次都拿到相同的（往往是空的）结果，
自己意识不到应该换策略。

**验收**：同一「工具名+规范化参数」连续第 3 次出现时，系统 MUST 拦截该次调用，
MUST 向消息序列注入一条说明（已重复调用、无新信息、请换策略或直接告知用户查不到），
且该工具 MUST 在本轮后续迭代中不再可用。

### User Story 2 - 触顶时给用户一个收尾，而不是一条错误 (Priority: P1)

今天跑满 5 轮迭代，用户看到的是一条错误。中间过程其实都在库里（逐轮落库），
但**没有任何收尾的答复**——会话历史里是一串工具调用，然后戛然而止。
用户不知道系统做了什么、为什么停了、已经查到了什么。

**验收**：触顶时 MUST 补一条**由程序拼接**的收尾助手消息并持久化，
MUST 以正常结束事件（`final` + `done`）收尾而非 `EventError`，
消息内容 MUST 说明本轮因工具调用次数达到上限而中止、信息可能不完整。

### User Story 3 - 正常对话行为逐字不变 (Priority: P1)

**验收**：没有触发重复检测、也没有跑满迭代上限的对话，其事件序列、消息内容与持久化结果
MUST 与本期上线前逐字一致。

### Edge Cases

- 触顶时本轮**一个字都没生成过**（每轮都只发工具调用）→ 仍然要发收尾消息。
  这恰恰是最需要收尾的情形：用户看到一串工具调用之后什么都没有，最容易以为系统坏了。
- 重复调用发生在**第一次**迭代（模型一上来就重复）→ 阈值按次数计，不因迭代序号特殊处理。
- 两个不同工具交替重复（A、B、A、B…）→ **本期不检测**。按「同一调用连续 N 次」判定，
  交替模式检测不到。这是已知盲区，见 Out of Scope。
- 同一工具但参数不同 → 不算重复，正常放行。
- 工具在本轮被禁用后，模型仍然要求调它 → 该次调用 MUST 被拒绝并返回一条工具结果说明，
  MUST NOT 静默丢弃（静默丢弃会让模型看不到任何反馈，更容易继续转圈）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 对每次工具调用计算「工具名 + 规范化参数」的指纹。
  规范化 MUST 是结构级（对象 key 递归排序后紧凑序列化），MUST NOT 做语义级等价判断。
- **FR-002**: 参数不是合法 JSON 时 MUST 退化为对原始字符串取指纹，MUST NOT 报错。
- **FR-003**: 同一指纹**连续**出现达到阈值（3）时 MUST 拦截，MUST NOT 执行该次工具调用。
- **FR-004**: 拦截时 MUST 向消息序列注入一条说明，内容 MUST 告知模型：
  该工具已用相同参数调用多次且无新信息，应更换策略或直接告知用户查不到。
- **FR-005**: 被拦截的工具 MUST 在本轮后续迭代中从可用工具列表移除。
- **FR-006**: 迭代触顶时，系统 MUST 追加一条程序拼接的收尾助手消息、持久化它，
  并以正常结束事件收尾，MUST NOT 发 `EventError`。
- **FR-007**: 触顶收尾的说明文案 MUST 由程序拼接，MUST NOT 依赖模型生成或遵守提示词。
- **FR-008**: 收尾消息 MUST NOT 携带任何 Citation——它不是基于检索证据生成的内容，
  给它挂引用会让一条程序拼接的文案看起来像有出处的回答。
- **FR-009**: 未触发上述任何路径时，行为 MUST 与本期上线前逐字一致。
- **FR-010**: 循环检测与触顶降级 MUST 记录到 trace，MUST NOT 记录工具参数原文
  （沿用既有脱敏口径，只记指纹前缀、重复次数、被禁用的工具名）。

### Key Entities

- **调用指纹（Call Fingerprint）**：`工具名 + 规范化参数` 的哈希，只在单轮对话内有意义，不持久化。

## Success Criteria *(mandatory)*

- **SC-001**: 存在一组用例：模型连续三次请求相同调用，第 3 次被拦截、注入了说明、
  且该工具在后续迭代中不再出现在请求的工具列表里。
- **SC-002**: 存在一组用例：迭代触顶时收到 `final` + `done`（而非 `error`），
  收尾消息被持久化且内容说明了「达到上限、信息可能不完整」。
- **SC-003**: 存在一组用例：触顶收尾消息不携带任何 Citation。
- **SC-004**: 既有 `conversation` 全部测试保持通过，正常对话路径逐字不变（FR-009）。
- **SC-005**: 指纹计算是纯函数并被单测覆盖，含参数非法 JSON、key 顺序不同但语义相同两种情况。

## Assumptions

- 不改 `maxToolCallIterations = 5` 这个值本身。
- 不引入 token 预算与墙钟超时（第一层的另外两半），见 Out of Scope。
- 不改 SSE 事件类型定义，只改「触顶时发哪一个既有事件」。

## Out of Scope

- **token 预算与墙钟超时**（第一层的另外两半）。它们改动面更大且与本期正交，单独立项。
- **让模型基于中间结果重新作答**（更进一步的第三层）。有填空式幻觉风险，需独立评估。
- **交替式循环检测**（A、B、A、B…）。本期只按「同一调用连续 N 次」判定。
- **跨轮次的循环检测**。指纹只在单轮内有效，不跨对话轮持久化。
- 语义级参数等价判断。
