# Feature Specification: PDF 版面感知解析与跨页分块

**Feature Branch**: `006-pdf-layout-chunking`

**Created**: 2026-09-04

**Status**: Draft

**Input**: User description: "PDF 与图片型文档的结构感知解析与分块。现状缺陷：chunkPDFPages 按页独立切分（chunk.go），页边界处段落被硬切成两半、overlap 不跨页携带、页眉页脚混入正文污染 embedding，导致跨页内容召回失败并诱发幻觉；图片型/扫描件 PDF 无文本层，当前完全无法入库。范围：一、抽取阶段保留行级结构线索（字号、Y 坐标）；二、剥离页眉页脚等版面噪音；三、跨页重建段落流，使 overlap 可跨页携带；四、页码从单值改为区间（page_start/page_end），保持引用诚实；五、按业界做法（Docling HierarchicalChunker/HybridChunker、MinerU layout model）评估「换解析层」与「Go 内启发式」两条路线并给出选型；六、图片型 PDF 单独判定为独立 pipeline（OCR 或视觉检索 ColPali），本期只做能力边界识别与明确降级，不实现。明确不做：多栏排版阅读顺序重建、跨页表格合并。"

## 问题陈述

Hify 现有的 PDF 处理把**页**当成了语义边界。这是一个物理排版单位，不是语义单位，由此产生三类可观察的损害：

1. **跨页段落被硬切**：一个跨越页边界的段落被切成两个不完整的片段，两半各自缺失上下文，检索时相似度都不足以进入结果——**应当被召回的内容检索不到**。
2. **重叠不跨页携带**：每一页独立走一次分块，页边界处连"重叠补救"这道保险都没有。
3. **版面噪音混入正文**：页眉、页脚、纯页码行被当作正文写进片段，既污染该片段的向量表示，又让不同页的片段因为共享同一段页眉而产生**虚假相似**。

第 1、3 项共同诱发幻觉：模型拿到一个在句子中间被截断的片段（例如"……因此该条款不适用于"），会自行把这句话补完。

此外，**图片型/扫描件 PDF 当前完全无法入库**——没有文本层，抽取结果为空，文档处理失败并返回"文档内容为空或无法提取到文本"。这个提示无法让用户区分"上传了一个空文件"和"上传了一份需要 OCR 的扫描件"。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 跨页内容能被检索到 (Priority: P1)

用户上传一份 PDF，其中某个关键说明的段落正好横跨第 3 页末尾和第 4 页开头。用户就这段说明提问，系统能够返回**完整**的这段内容，并如实标注它出自第 3-4 页。

**Why this priority**: 这是本功能的核心价值。跨页内容检索不到，是当前实现最直接、最高频的失效方式，也是本次改动唯一无法用其它手段绕开的问题。

**Independent Test**: 准备一份关键段落跨页的 PDF，入库后就该段落提问，断言检索结果中存在一个包含完整段落的片段。此项在当前实现上必须失败。

**Acceptance Scenarios**:

1. **Given** 一份 PDF 中某段落横跨两页，**When** 该文档完成入库，**Then** 该段落存在于同一个片段中，未被页边界切断
2. **Given** 上述片段被检索命中，**When** 系统展示引用信息，**Then** 引用标注为该片段实际覆盖的页码范围（如"第 3-4 页"），而不是任选其一
3. **Given** 一个段落在页内自然结束（以句末标点收尾），**When** 处理下一页，**Then** 两页内容不被错误地粘连成一段

---

### User Story 2 - 页眉页脚不进入正文 (Priority: P1)

用户上传一份每页都带页眉（章节名）和页脚（页码、公司名）的 PDF。检索结果中的片段只包含正文，不包含这些每页重复的版面元素。

**Why this priority**: 与 P1 同级，因为它同时影响**召回质量**（噪音稀释向量语义）和**结果质量**（虚假相似导致不相关片段被召回）。且它与 User Story 1 相互独立——即使不做跨页合并，单独剥离噪音也能带来可度量的收益。

**Independent Test**: 准备一份带固定页眉页脚的多页 PDF，入库后检查产出的片段文本，断言不含页眉页脚文字。

**Acceptance Scenarios**:

1. **Given** 一份 PDF 每页顶部都有相同的章节名，**When** 文档完成入库，**Then** 产出的片段正文中不含该章节名
2. **Given** 一份 PDF 每页底部有形如"第 X 页 / 共 Y 页"的页码行，**When** 文档完成入库，**Then** 该行不出现在任何片段中
3. **Given** 某段正文恰好出现在页面顶部但**不**跨页重复，**When** 文档完成入库，**Then** 该段正文被保留，不被误判为页眉
4. **Given** 系统剥离了某些内容，**When** 处理完成，**Then** 被剥离的内容有可供事后核查的记录

---

### User Story 3 - 引用信息保持诚实 (Priority: P2)

用户看到一条引用时，页码信息要么准确，要么明确缺失，**绝不出现编造的页码**。跨页片段标注为页码区间。

**Why this priority**: 引用诚实是现有实现刻意保护的性质（当前按页切分正是为此），本次改动不能以牺牲它为代价。但它依附于 P1 的产出，无法脱离 P1 单独交付价值，故列为 P2。

**Independent Test**: 检查所有产出片段的页码区间：起始页 ≤ 结束页，且都落在文档实际页数范围内。

**Acceptance Scenarios**:

1. **Given** 一个片段只覆盖单页，**When** 展示引用，**Then** 显示单个页码（不显示为区间）
2. **Given** 一个片段跨越多页，**When** 展示引用，**Then** 显示完整覆盖的页码区间
3. **Given** 非 PDF 格式的文档（Markdown、纯文本），**When** 展示引用，**Then** 无页码信息，且系统不为其编造页码

---

### User Story 4 - 章节标题作为上下文保留 (Priority: P3)

PDF 中的标题层级被识别出来，**并像 Markdown 那样拼进片段正文一起参与向量化**，使得"它支持三种模式"这类依赖标题才能理解的片段能够被正确检索到。

**Why this priority**: 收益明确但可选。它依赖排版特征推断，可靠性天然低于前三项；识别不出时降级为无标题，不影响其它功能。**优先级低于前三项，且允许在实现阶段被裁掉。**

**Independent Test**: 准备一份有明确标题层级的 PDF，断言标题下方片段的**正文内容本身**（而非仅元数据字段）包含该标题路径。

**Acceptance Scenarios**:

1. **Given** 一份带标题层级的 PDF，**When** 文档完成入库，**Then** 标题下方片段的正文中包含其标题路径，且该路径参与了向量化
2. **Given** 一份没有可辨识标题结构的 PDF，**When** 文档完成入库，**Then** 片段的标题信息为空，系统不编造标题
3. **Given** 标题路径与正文之和超过片段长度上限，**When** 组装片段，**Then** 正文完整保留、标题路径缩短或丢弃（与既有 Markdown 路径同一优先级规则）

---

### User Story 5 - 扫描件给出可行动的提示 (Priority: P2)

用户上传一份扫描件 PDF，系统明确告知"这是无文本层的扫描件，当前不支持"，而不是笼统的"内容为空"。

**Why this priority**: 本期**不实现** OCR 或视觉检索。此项的全部价值在于把一个让人困惑的失败变成一个可行动的提示，成本极低、收益明确。

**Independent Test**: 上传一份纯图片 PDF，断言返回的错误信息明确指向"扫描件/无文本层"，与空文件的提示不同。

**Acceptance Scenarios**:

1. **Given** 一份所有页面都无可提取文本的 PDF，**When** 用户上传，**Then** 系统给出明确区分于"空文件"的中文提示
2. **Given** 一份部分页面是扫描图、部分页面有文本的 PDF，**When** 用户上传，**Then** 有文本的部分正常入库，且用户被告知有部分页面未能提取

---

### Edge Cases

- **单页 PDF**：不存在跨页合并场景，行为必须与改动前一致
- **页面之间没有任何可合并处**（每页都以完整句子结束）：产出应与按页切分基本一致
- **整篇没有句末标点的文档**（某些表格型或列表型 PDF）：不得因此把全文合并成一个超长段落——长度硬上限必须仍然生效
- **页眉页脚与正文文字完全相同**：宁可漏剥，不可误删正文
- **只有两页的文档**：重复率判据在极少页数下不可靠，需要有最小页数门槛
- **超长单段落跨越三页以上**：合并后仍必须服从片段长度上限，超出时回退定长切分
- **文档页数极多**：噪音识别需要跨页统计，不得因此让处理时间不可接受
- **已入库的存量 PDF 文档**：改动后其页码字段与新逻辑的语义差异如何处理

## Requirements *(mandatory)*

### Functional Requirements

**跨页连续性**

- **FR-001**: 系统 MUST 在页边界处判断上一页末尾的内容是否为未结束的段落，是则与下一页开头合并为同一段
- **FR-002**: 系统 MUST 使重叠内容能够跨越页边界携带
- **FR-003**: 系统 MUST 在合并判断不成立时保持段落分开，不得无条件合并所有页
- **FR-004**: 合并后的内容 MUST 仍然服从片段长度上限；单个合并段落超限时 MUST 回退到既有的定长切分

**版面噪音剥离**

- **FR-005**: 系统 MUST 识别并剥离跨页重复出现的页眉、页脚内容
- **FR-006**: 系统 MUST 识别并剥离纯页码行
- **FR-007**: 噪音判定 MUST 同时满足多个独立条件（位置、重复率、长度）才成立——单一条件不足以剥离
- **FR-008**: 系统 MUST 记录被剥离的内容，供事后核查
- **FR-009**: 页数少于设定门槛时，系统 MUST 跳过基于重复率的噪音判定，不做剥离

**引用诚实性**

- **FR-010**: 每个片段 MUST 记录其实际覆盖的页码范围（起始页与结束页）
- **FR-011**: 系统 MUST NOT 为跨页片段任选一个页码作为其归属
- **FR-012**: 片段的起始页 MUST 小于等于结束页，且两者都 MUST 落在文档实际页数范围内
- **FR-013**: 起始页与结束页相同时，引用展示 MUST 呈现为单个页码而非区间
- **FR-014**: 系统 MUST NOT 为不支持页码概念的文档格式生成页码

**标题识别（可选能力）**

- **FR-015**: 系统 SHOULD 识别 PDF 中的标题，并将标题路径**拼接进片段正文**、随正文一起参与向量化——**仅写入元数据字段不满足本条**，因为向量化只作用于片段正文
- **FR-015a**: 标题路径与正文长度冲突时，系统 MUST 优先保全正文，由标题路径缩短或丢弃（与既有 Markdown 路径的规则一致）
- **FR-016**: 标题无法可靠识别时，系统 MUST 留空而非编造

**扫描件识别**

- **FR-017**: 系统 MUST 区分"文档为空"与"文档无可提取文本层（扫描件）"两种失败，并给出不同的中文提示
- **FR-018**: 部分页面无文本层时，系统 MUST 处理有文本的部分，并告知用户有页面未能提取
  - ⏸️ **Deferred（2026-09-04 所有者裁决）**：本条整体推迟到下一期，不在 006 范围内。
    本期只做 FR-017（整份扫描件的专用提示）。原因是 `documents` 表没有承载"成功但有提示"
    的字段（`MarkDocumentReady` 硬编码 `error_message = NULL`），补齐它需要 MySQL migration
    + DTO + 前端文档列表展示，与 US5 的边际价值不成比例——US5 的价值几乎全在纯扫描件。
    本期对"部分页无文本层"的实际行为：有文本的部分正常入库 + 一条结构化日志，
    **用户界面看不到提示**。详见 plan.md「三项拍板」决策 1。
- **FR-019**: 本期 MUST NOT 实现 OCR 或视觉检索能力

**行为兼容**

- **FR-020**: 非 PDF 格式（Markdown、纯文本）的处理行为 MUST 保持不变
- **FR-021**: 相同的 PDF 输入 MUST 产出相同的片段序列与页码归属（确定性）
- **FR-022**: 存量已入库文档 MUST 保持可检索，其页码信息 MUST 保持有效

### 需要在 `plan.md` 中解决的开放决策

以下决策超出规格层（涉及技术路线），**必须**在 `/speckit-plan` 阶段作出并记录理由：

- **D-001 · 解析路线**：在"Go 进程内基于排版特征的启发式实现"与"外部专用文档解析器（Docling / MinerU 一类）把 PDF 先转成带结构的中间格式"之间选择。后者版面还原质量显著更高（业界普遍采用视觉版面检测模型，而非排版启发式），但会引入 Go 之外的运行时依赖，与"打包成单个 Go 二进制"这一既有工程约束冲突。**此决策直接影响 FR-015 的可达质量。**
- **D-002 · 存量数据处理**：新逻辑仅对新入库文档生效，还是对存量文档回填/重建。

### Key Entities

- **页行（Page Line）**：抽取阶段的最小单位，携带文本内容、所属页码，以及用于噪音与标题判定的排版特征
- **段落流（Paragraph Stream）**：跨页重建后的连续内容序列，是分块的真正输入；每个单元记录其覆盖的页码范围
- **片段（Chunk）**：入库与检索的单位。相较现状，其页码归属从**单值**变为**区间**
- **版面噪音记录（Layout Noise Record）**：被剥离内容的审计记录，用于事后核查误删

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对于关键内容跨页的 PDF，该内容能够被一次检索命中并以完整形态返回——此项在改动前为失败
- **SC-002**: 带固定页眉页脚的 PDF，入库后产出的片段中页眉页脚文字出现次数为 **0**
- **SC-003**: 产出片段的页码区间 **100%** 满足"起始页 ≤ 结束页且均在文档页数范围内"
- **SC-004**: 同一份 PDF 连续处理两次，产出的片段序列与页码归属**逐字节一致**
- **SC-005**: 正文误删率为 **0**——噪音剥离不得移除任何仅出现在单页的内容
- **SC-006**: 非 PDF 格式文档的检索行为与改动前**完全一致**（既有确定性检索门禁逐字节不变）
- **SC-007**: 上传扫描件 PDF 时，用户看到的提示能够让其判断下一步动作（需要 OCR），无需查阅日志
- **SC-008**: 单份 PDF 的入库处理时间相比改动前增加不超过 **50%**

## Assumptions

- **文档语言与形态**：主要面向单栏排版的中英文文档。多栏排版的阅读顺序还原**明确不在本次范围内**——它需要独立的版面分析能力，是另一量级的工作。
- **跨页合并的取舍方向**：合并判断使用启发式，必然存在误判。**代价不对称——错误合并最多导致一个片段包含两个主题，错误切断则直接导致内容检索不到**，因此判定偏向"倾向合并"。
- **噪音剥离的取舍方向**：与上一条相反，**偏向保守**——宁可漏剥噪音，不可误删正文（SC-005）。
- **跨页表格合并不在范围内**：识别"表格续页"并合并表头，是独立且更复杂的问题，另立任务。
- **视觉检索路线不在范围内**：把页面当图像做多向量嵌入（ColPali 一类）是与文本抽取并行的另一条完整流水线，不在本次范围内；本期仅做能力边界识别与明确降级（FR-017 ~ FR-019）。
- **既有的分块长度约束继续有效**：片段长度上限、单文档片段数上限等既有保护不因本次改动放宽。
- **回归验证依赖既有的确定性检索门禁**：用于证明非 PDF 路径行为未变（SC-006）。
- **不改变检索、融合、准入、重排等下游环节**：本次改动全部发生在文档入库阶段。
