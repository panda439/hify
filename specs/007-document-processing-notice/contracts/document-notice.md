# 契约：文档响应的处理提示字段与展示

**Feature**: `007-document-processing-notice` | **Date**: 2026-09-05

本功能**不新增任何 HTTP 端点、不新增任何请求参数**，但它改变了既有响应体的形状，
那同样是契约变更，必须成文。

**受影响的端点**：`GET /api/v1/knowledge-bases/{id}/documents`（文档列表）
以及任何返回单份文档的既有端点。

---

## 1. 响应体

```jsonc
{
  "id": "...",
  "file_name": "contract.pdf",
  "file_type": "pdf",
  "status": "ready",
  "error_message": "",
  "chunk_count": 128,
  "unextracted_pages": [46, 47, 48, 49, 50],   // 新增
  "created_at": "...",
  "updated_at": "..."
}
```

### 1.1 契约条款

| # | 条款 |
|---|---|
| C1 | `unextracted_pages` 是**未能提取文本的页码**，1-indexed、**升序**、去重 |
| C2 | `null` 或 `[]` 表示"无提示"。⚠️ 后端**只发 `null` 或非空数组**，绝不发空数组；前端两者都要当作"无提示"处理，因为存量数据与未来改动都可能让空数组出现 |
| C3 | `null` 同时覆盖两种情况：这次处理没有缺页，以及这份文档从未被本功能上线后的版本处理过。**系统不区分它们，因为它确实不知道**（FR-015） |
| C4 | 它**不是错误**。`status` 仍为 `ready`，文档可正常检索。失败原因走 `error_message`，两条通道完全独立（FR-002） |
| C5 | `status != "ready"` 时，`unextracted_pages` **MUST NOT 被展示**——那可能是上一次成功留下的值（FR-005） |
| C6 | 非 PDF 文档恒为 `null`（FR-014） |
| C7 | `error_message` 的语义、取值与呈现**一字不变**（R3） |

⚠️ **C5 是最容易漏的一条**：字段本身可能有值（上一次成功时写的），
但当前这次处理失败了。**判断依据是 `status`，不是字段是否有值。**

---

## 2. 前端展示契约

**现状**（`knowledge-documents-dialog.tsx:103`）：

```tsx
{d.status === "ready" ? `${d.chunk_count} 个分片` : d.status === "failed" ? d.error_message : "—"}
```

**改后的规则**：

| 条件 | 展示 |
|---|---|
| `status === "ready"` 且无缺页 | `${chunk_count} 个分片` — **与改动前逐字节一致**（FR-010 / SC-004） |
| `status === "ready"` 且有缺页 | `${chunk_count} 个分片` + 一条**提示**（形态见 §2.1） |
| `status === "failed"` | `error_message` — **与改动前逐字节一致**（C7） |
| 其他 | `—` — 不变 |

### 2.1 提示的呈现要求（FR-007）

| 要求 | 为什么 |
|---|---|
| MUST 与"失败"在视觉上**明确不同** | 做成看起来像失败，用户会以为文档不可用而去删掉重传 |
| MUST 仍将文档呈现为**可用** | 它就是可用的——128 个分片都在，能检索 |
| MUST NOT 弱到被忽略 | 太弱等于没做，US1 白做且不会有人来报 bug |
| MUST 说明**有多少页**（真实总数） | FR-009 |
| MUST 让用户判断得出**下一步动作** | FR-008——他要知道该对哪几页做 OCR |

**页码列举的截断**：界面可以只列前几页再折叠成"等 N 页"，
但 **N 必须是真实总数**。截断的是列举，不是事实。

### 2.2 ⚠️ 前端不得做的三件事

1. **不得**在 `status !== "ready"` 时展示这个字段（C5）。
2. **不得**把提示做成 `status` 的第五种取值。`status` 的取值集合（`pending`/`processing`/`ready`/`failed`）
   由数据库 CHECK 约束固定，且它表达的是**文档可不可用**——带提示的文档是可用的。
   提示是可用文档的一个附加说明，不是一种新状态。
3. **不得**把 `unextracted_pages` 的长度当成"缺失内容的重要程度"来决定要不要显示。
   缺 1 页和缺 50 页都要显示——用户判断重要程度，不是界面替他判断。

## 3. 不受影响的契约（逐条确认，不是遗漏）

| 契约 | 为什么不受影响 |
|---|---|
| 检索 / 对话 / 引用 | 本功能不触碰 `chunks`、不触碰检索链路。⚠️ 这也意味着**用户在对话里问到缺失内容时仍然只会得到"检索不到"**——本功能让他能在上传后预先知道，不改善那个体验 |
| `status` 的取值集合 | 不新增取值（见 §2.2 第 2 条） |
| `error_message` | 一字不变（C7） |
| 文档上传 / 重试 / 删除的入参与行为 | 不变 |
| PostgreSQL 侧一切 | 零改动 |

---

## 4. 错误响应

**本功能不新增任何错误码。** 它表达的是成功，不是失败。
纯扫描件继续走 006 的 `knowledge.pdf_no_text_layer`（失败路径），文案一字不改。
