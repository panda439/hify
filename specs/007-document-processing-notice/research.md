# Phase 0 · 技术调研与关键决策：文档处理的「成功但有提示」通道

**Feature**: `007-document-processing-notice` | **Date**: 2026-09-05

本文解决 `spec.md` 遗留的两项开放决策（D-001 / D-002）。

---

## R1 · 提示的粒度与承载形态（对应 D-001）

**Decision**：新增**一列** `documents.unextracted_pages`，存**未能提取文本的页码列表**
（升序、逗号分隔、1-indexed），`NULL` 表示"没有缺页"。**不存渲染好的句子。**

**Rationale**：

1. **用户的下一步动作是「把那几页做 OCR」，光给个数量他不知道该 OCR 哪几页。**
   FR-008 要求提示能让用户判断下一步动作——"有 5 页未能提取"能让他知道**有事**，
   但不能让他**做事**。页码是这条提示从"警告"变成"可执行"的那一半。
2. **数量由列表长度导出**（FR-009），不单独存。两个字段表达同一件事，早晚会不一致。
3. **不存渲染好的句子**：那会把展示层烧进数据。文案改一次，所有存量行都还留着旧文案，
   而它们表达的事实其实没变。存事实、渲染时成句。
4. **不需要截断**：页码数量的上界是文档页数，一份 1000 页文档全缺也就约 4000 字符，
   `TEXT` 放得下。**截断是展示层的事**（界面只列前几页 + "等"），不是存储层的事——
   存储层一旦截断，真实数量就永久丢了。

**⚠️ 与既有约定的关系（不是冲突）**：`errors.go` 有一条约定"`Message` 是固定的，
任何动态细节——计数、文件路径——进日志"。**那条约定管的是哨兵错误**：`apperr.AppError`
是包级变量，每个实例全局共享一份 `Message`，塞进动态内容在物理上就不成立。
本功能的提示是**每份文档各自的数据**，不是哨兵，那条约定对它没有作用面。

**Alternatives considered**：

| 方案 | 否决理由 |
|---|---|
| 只记数量（`unextracted_page_count INT`） | 用户知道有事发生，但不知道该对哪几页做 OCR。把一条可执行的提示降级成一条焦虑 |
| 存渲染好的中文句子 | 展示层烧进数据；文案一改，存量行就成了历史文案的化石 |
| JSON 列 + 一个 `code` 字段（`{"code":"no_text_layer","pages":[46,47]}`） | **这是通用警告框架的种子，FR-011 明确禁止。** 一个 `code` 字段的存在本身就在邀请第二种、第三种警告搭便车，而它们从来没被设计过 |
| 单开一张 `document_notices` 表 | 一份文档至多一条当前提示、不累积历史（spec 的 Assumptions），一张表在表达一个一对一关系，纯粹的复杂度 |

⭐ **列名就是它的语义**：`unextracted_pages` 只能装"哪些页没提取出文本"。
第二种警告想复用它会立刻显得荒谬——**这正是要的效果**（FR-011）。
它得自己开一列，而开列这个动作会强制一次真正的设计讨论，而不是搭便车。

## R2 · 陈旧提示的清除时机（对应 D-002）

**Decision**：把 `unextracted_pages` 的写入**并进 `MarkDocumentReady` 这条既有语句**，
不新增任何清除步骤。

**Rationale**：

`MarkDocumentReady` 已经是"一个版本成为 ready"的**唯一**入口，而且它已经带着本功能
需要的全部保证：

```sql
UPDATE documents
SET status = 'ready', error_message = NULL, chunk_count = ?, lease_expires_at = NULL
WHERE id = ? AND version = ? AND status = 'publishing';
```

- **`WHERE version = ? AND status = 'publishing'`** 保证写进去的提示属于**最终生效的那一次**
  处理，而不是被淘汰的那次（spec 的 Edge Case「同一份文档并发处理」）。
- **它已经在无条件清 `error_message`**——把 `unextracted_pages = ?` 加在旁边，
  语义完全对称：**每次成功都整体覆盖，没有缺页就写 NULL**。FR-004（无缺页时清除）
  因此是**免费得到的**，不需要任何额外代码，也不新增任何并发面。
- **0 行受影响**的既有含义（别的 runner 抢先完成了，良性幂等竞争）一字不变。

**Alternatives considered**：

| 方案 | 否决理由 |
|---|---|
| 单独一条 `ClearDocumentNotice` 语句 | 凭空多一次写、多一个"它和 MarkDocumentReady 谁先谁后"的问题。两条语句之间没有事务，就有窗口 |
| 在 `ProcessDocument` 里提前写 | 那时版本还没赢下发布，写进去的可能是被淘汰那次的结果 |
| 在读取时按需推导 | 推导不出来——`chunks` 里没有"这一页没提取到"这条信息，缺页在分块阶段就已经消失了 |

## R3 · 失败路径与提示路径必须完全分离

**Decision**：`error_message` 的语义、写入时机、呈现方式**一字不改**。
提示走一条**平行**的新通道，两者在数据上和展示上都不共用任何东西。

**Rationale**：复用 `error_message` 承载提示（哪怕 status 仍是 ready）是最省事的做法，
也是最坏的：字段名与语义打架，`MarkDocumentReady` 的 `error_message = NULL` 要改成条件写入，
而前端 `d.status === "failed" ? d.error_message : "—"` 这类判断会散落成一堆特例。
更要紧的是 FR-002：**一份文档不得因为携带提示而被视为失败**——共用字段就是在邀请这个混淆。

---

## R4 · 存量文档不追溯标记（对应 FR-015）

**Decision**：迁移只加列，`NULL` 即"不知道"。**不做任何回填。**

**Rationale**：系统并不知道一份从未重新处理过的存量文档当初有没有缺页——那个信息
在当时的抽取阶段就没被记录。凭空给它标提示是编造；标"没有缺页"同样是编造。
`NULL` 是唯一诚实的值，且它天然渲染为"无提示"，与改动前的呈现完全一致（FR-010）。

用户对某份文档存疑时，**重新处理**它就能拿到准确的提示——这是既有能力，不需要新入口。

---

## R5 · 展示形态

**Decision**：文档列表在**既有的那一列**（现在显示 `${chunk_count} 个分片`）后面追加提示，
不新增列、不新增弹窗、不做通知中心。

**Rationale**：spec 的 Assumptions 已定"提示是处理结果的一部分，不是独立的通知系统"。
用户下次看文档列表时看到它就够了。

**呈现要求**（FR-007）：提示必须**明确区别于失败**，且文档仍呈现为**可用**。
具体形态在 `contracts/` 里定。页码列表在界面上**截断展示**（列前几页 + "等 N 页"），
但**数量必须是真实总数**——截断的是列举，不是事实。

## 阈值与常量

| 常量 | 用途 |
|---|---|
| 界面页码列举上限 | 超出则折叠为"等 N 页"，防止一份大量缺页的文档把整行撑爆 |

只有这一个，且**只作用于展示**。存储层不截断（R1）。
