# Feature Specification: 文档处理的「成功但有提示」通道

**Feature Branch**: `007-document-processing-notice`

**Created**: 2026-09-05

**Status**: Draft

**Input**: User description: "文档处理的「成功但有提示」通道。现状缺陷：documents 表只有 error_message，而 MarkDocumentReady 的 SQL 硬编码 error_message = NULL——一份成功入库的文档在数据模型上没有任何字段能表达「处理完成了，但有话要对用户说」。直接后果是 006 遗留的 FR-018 无法实现：部分页面无文本层的 PDF（例如 50 页合同里后 5 页是扫描的签字页），有文本的 45 页正常入库、文档状态显示「就绪」，而界面上一个字都不会提有 5 页没进去。用户以为整份文档都在知识库里，问附件条款时什么都召不回来——一个静默的缺失比一个明说的失败危险得多。范围：一、给 documents 增加承载「成功但有提示」的字段；二、ProcessDocument 在部分页无文本层时写入该提示；三、前端文档列表把提示显示出来，与「失败」在视觉上明确区分；四、提示文案必须让用户判断得出下一步动作。明确不做：OCR、视觉检索、把这条通道扩展成通用的文档处理警告框架。"

## 问题陈述

系统当前只能表达两种处理结局：**成功**，和**失败**。它无法表达第三种，而第三种真实存在：

> 处理完成了，文档可用，**但有一部分内容没能进去**。

这不是理论上的缺口。006-pdf-layout-chunking 已经实现了「部分页面无文本层时，处理有文本的部分」——一份 50 页合同，前 45 页是电子文本、后 5 页是扫描进来的签字页，现在会把 45 页正常入库。**但用户看到的是「就绪」，界面上一个字都不会提那 5 页。**

后果是一个**静默的缺失**：

1. 用户以为整份合同都在知识库里了。
2. 他就附件里的条款提问，检索什么都召不回来。
3. 在他看来，要么是系统不好使；要么更糟——模型拿着不完整的上下文照样给了一个答案。

**一个明说的失败让人知道下一步做什么；一个静默的缺失让人对整个系统失去校准。** 后者危险得多，因为它不会在任何地方留下痕迹让人发现。

根因在数据模型：`documents` 表只有 `error_message` 一个字段承载"要对用户说的话"，而它的语义与 `status = failed` 绑死；`MarkDocumentReady` 的 SQL 更是硬编码 `error_message = NULL`。**一份成功入库的文档，在数据模型上没有任何位置可以挂一条提示。** 信息目前只落在结构化日志里——那是给开发者看的，不是给上传文档的人看的。

这条要求在 006 里编号 FR-018，被明确推迟到本期（见 006 的 plan.md「三项拍板」决策 1）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 部分内容没进去时，用户能看见 (Priority: P1)

用户上传一份部分页面是扫描图的 PDF。文档正常入库、状态是「就绪」、可以正常检索——**同时**，文档列表上有一条明确的提示，告诉他有多少页没能提取，以及可以做什么。

**Why this priority**: 这是本功能存在的全部理由。其余每一条要求都是为了让这一条成立。

**Independent Test**: 上传一份部分页无文本层的 PDF，在文档列表上断言这条提示可见，且它与"处理失败"在视觉上不是同一个东西。

**Acceptance Scenarios**:

1. **Given** 一份 50 页 PDF 其中 5 页无文本层，**When** 处理完成，**Then** 文档状态为「就绪」且可正常检索
2. **Given** 上述文档，**When** 用户查看文档列表，**Then** 看到一条提示说明有页面未能提取
3. **Given** 上述提示，**When** 用户读它，**Then** 能判断出下一步动作（把那些页做 OCR 后重新上传），无需查阅日志或询问他人
4. **Given** 一份**全部**页面都正常的文档，**When** 处理完成，**Then** **不显示**任何提示——没有话要说的时候就不要说话

---

### User Story 2 - 提示与失败不会被混淆 (Priority: P1)

用户一眼能分清「这份文档处理失败了，现在不可用」和「这份文档可用，但有一部分没进去」。

**Why this priority**: 与 US1 同级。把提示做成看起来像失败，用户会以为文档不能用而去重传或删除；做得太弱又会被忽略，等于没做。**这条要求的成败决定了 US1 的提示是否真的起作用**，但它可以独立验收。

**Independent Test**: 同一个列表里同时放一份失败文档和一份带提示的就绪文档，断言两者的状态呈现不同，且带提示的那份仍呈现为可用。

**Acceptance Scenarios**:

1. **Given** 列表里同时有失败文档与带提示的就绪文档，**When** 用户查看，**Then** 两者的呈现明确不同
2. **Given** 一份带提示的就绪文档，**When** 用户查看，**Then** 它仍然被呈现为**可用**，而不是需要修复
3. **Given** 一份失败文档，**When** 用户查看，**Then** 失败信息的呈现方式与改动前**保持不变**

---

### User Story 3 - 提示随重新处理而更新 (Priority: P2)

用户把缺失的页做了 OCR 后重新上传或重新处理该文档，提示随之消失；反之，一份原本正常的文档若被替换成有扫描页的版本，提示随之出现。

**Why this priority**: 提示如果只增不减，它很快就会变成一条没人相信的陈旧信息——用户按提示做了 OCR、重传，提示还在，那这条提示就废了。但它依附于 US1 的产出，无法脱离 US1 单独交付价值。

**Independent Test**: 对同一份文档先后处理两个版本（一个有扫描页、一个没有），断言提示相应出现和消失。

**Acceptance Scenarios**:

1. **Given** 一份带提示的文档，**When** 它被重新处理且新版本所有页都有文本，**Then** 提示消失
2. **Given** 一份无提示的文档，**When** 它被重新处理且新版本有页面无文本层，**Then** 提示出现
3. **Given** 一次处理失败，**When** 用户查看，**Then** 显示的是失败信息，不是上一次成功时留下的旧提示

---

### Edge Cases

- **全部页面都无文本层**：这是「纯扫描件」，属于**失败**而不是提示（006 的 FR-017 已实现，返回点名 OCR 的错误）。本功能不得把它改成「成功但有提示」
- **只有 1 页无文本层的 100 页文档**，与**只有 1 页有文本层的 100 页文档**：后者虽然技术上属于"部分"，但对用户而言几乎等同于扫描件——提示文案是否需要区分这两种程度
- **非 PDF 格式**（txt / md）：没有"页面"概念，永远不产生提示
- **提示存在期间文档被删除或知识库被删除**：提示不得成为阻止删除的理由
- **同一份文档并发处理**（重试与原任务竞争）：提示必须对应**最终生效的那一次**处理，不能是被淘汰的那次留下的
- **缺失页数极多**：提示文案不得因为要列举页码而变得无法阅读

## Requirements *(mandatory)*

### Functional Requirements

**承载与写入**

- **FR-001**: 系统 MUST 能够为一份**处理成功**的文档记录一条面向用户的提示信息
- **FR-002**: 这条提示 MUST 与「处理失败的原因」在数据上是可区分的两件事——一份文档 MUST NOT 因为携带提示而被视为失败
- **FR-003**: 系统 MUST 在文档处理成功且存在未能提取的页面时写入该提示
- **FR-004**: 系统 MUST 在文档处理成功且不存在任何未能提取的页面时**清除**此前可能存在的提示
- **FR-005**: 处理失败时，用户看到的 MUST 是失败原因，MUST NOT 是上一次成功时留下的旧提示

**呈现**

- **FR-006**: 用户 MUST 能在查看文档列表时看到该提示，无需进入任何详情页或查阅日志
- **FR-007**: 提示的呈现 MUST 与"处理失败"在视觉上明确区分，且 MUST 仍将文档呈现为可用
- **FR-008**: 提示内容 MUST 让用户判断得出下一步动作
- **FR-009**: 提示 MUST 说明**有多少**内容未能提取，而不只是"有内容未能提取"
- **FR-010**: 没有提示时，文档的呈现 MUST 与本功能上线前**完全一致**

**范围约束**

- **FR-011**: 本期 MUST 只承载「部分页面无文本层」这一种情形。任何其他文档处理警告 MUST NOT 借用这条通道，直到有独立的规格论证过它
- **FR-012**: 本期 MUST NOT 实现 OCR 或视觉检索能力
- **FR-013**: 全部页面都无文本层的文档 MUST 继续作为**失败**处理（006 的 FR-017），MUST NOT 改判为「成功但有提示」
- **FR-014**: 非 PDF 格式的文档 MUST NOT 产生任何提示
- **FR-015**: 存量已入库文档 MUST 保持可用，且 MUST NOT 因本次改动被追溯地标上提示——没有重新处理过的文档，系统并不知道它当初有没有缺页

### 需要在 `plan.md` 中解决的开放决策

- **D-001 · 提示的粒度**：只记「有 N 页未能提取」，还是连**哪几页**一并记下。后者对用户更有用（他知道该去 OCR 哪几页），但页数极多时会让承载字段和界面都变得难看，且与「Message 不携带动态内容」的既有错误文案约定张力更大。
- **D-002 · 陈旧提示的清除时机**：FR-004 要求"处理成功且无缺页时清除"，但重新处理是一条有并发保护的状态机（claim / lease / publish）。清除动作挂在哪一步、由谁保证它与最终生效的那次处理一致，需要在 plan 里定死。

### Key Entities

- **文档处理提示（Processing Notice）**：一条依附于**成功**处理结果的、面向用户的信息。与"失败原因"是两个独立的概念，尽管两者都是"要对用户说的话"。它随每一次处理结果被整体覆盖，不累积历史。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 上传一份部分页面无文本层的文档后，用户**无需查阅日志**即可知道有内容未进入知识库——此项在改动前为失败
- **SC-002**: 用户看到提示后能说出下一步动作（对缺失页做 OCR 后重新上传）
- **SC-003**: 在同时包含「失败文档」与「带提示的就绪文档」的列表中，用户能正确区分两者，且不会把后者误判为不可用
- **SC-004**: 所有页面都正常的文档，其呈现与本功能上线前**逐字节一致**——不产生任何新的视觉噪音
- **SC-005**: 一份文档重新处理后不再缺页时，提示消失；提示与文档的**当前**状态 **100%** 一致，不存在陈旧提示
- **SC-006**: 纯扫描件（全部页无文本层）仍然作为失败呈现，其错误文案与 006 上线时**完全一致**
- **SC-007**: 非 PDF 文档、以及未重新处理过的存量文档，**0** 条提示

## Assumptions

- **本功能只解决"说不出话"这个缺口**，不改变任何处理逻辑：哪些页能提取、提取得对不对，全部由 006 已实现的逻辑决定，本期一行不改。
- **提示是处理结果的一部分，不是独立的通知系统**：不推送、不进消息中心、不需要"已读"状态。用户下次看文档列表时看到它就够了。
- **提示随处理结果整体覆盖，不累积**：一份文档任何时刻至多有一条当前提示，没有历史列表。
- **失败路径完全不动**：`error_message` 的语义、写入时机、呈现方式保持原样。本功能只新增一条平行的通道。
- **"有多少内容未能提取"以页为单位**：这是 006 的抽取阶段唯一能诚实给出的粒度。
- **不做通用化**：本期只有一个生产者（部分页无文本层）。把它做成通用的"文档处理警告框架"是在没有第二个用例的情况下提前抽象，FR-011 明确禁止。
- **验证依赖既有的确定性检索门禁**：用于证明检索行为未变（本功能不触碰检索链路）。
