# Feature Specification: 解析失败的页面也要能被用户看见

**Feature Branch**: `008-unparseable-page-notice`

**Created**: 2026-09-05

**Status**: Draft

**Input**: 007 交付后发现的口子（007 报告 §6.3）：一个页面进不了知识库有**两种**方式——
无文本层（扫描图），以及**解析时让 PDF 库崩溃、被逐页跳过**（006 加的 recover 兜底）。
**只有前者会产生提示。** 实测一篇 15 页 arXiv 论文第 1 页解析失败被跳过，用户看不到任何提示。
外加 007 报告 §6.2 的同类问题：被 reconciliation 恢复的文档拿不到任何提示。

## 问题陈述

007 建立了「成功但有提示」这条通道，用来解决一个静默的缺失：文档处理完成、状态显示就绪，
而用户不知道有一部分内容没进去。它解决了**一种**缺失。

**还有第二种，而且它现在完全不可见。**

一个页面进不了知识库有两条路：

| 缺失方式 | 现状 | 用户的下一步动作 |
|---|---|---|
| 页面**没有文本层**（扫描图） | ✅ 007 已提示 | 用 OCR 工具转换后重新上传 |
| 页面**解析失败**被跳过 | ❌ **完全不可见** | OCR 没用——那一页是损坏或不受支持的结构，得换工具重新导出 |

第二条路不是理论上的：006 给 `rsc.io/pdf` 的 panic 加了逐页 recover 兜底（在那之前整份文档
直接 panic），被跳过的页因此**在统计"有没有文本层"之前就已经消失了**。实测一篇 15 页的
arXiv 论文，第 1 页解析失败被跳过，剩下 14 页全部有文本——于是"缺页列表"为空，
**用户看到一份"就绪、无提示"的文档，而第 1 页根本不在里面**。

这正是 007 想消灭的那种静默缺失，只是换了个原因。**007 覆盖的是两种缺失里的一种。**

### 为什么不能直接塞进现有的那一列

第一反应是把解析失败的页也放进 `unextracted_pages`——列名字面上覆盖得住（"没被提取出文本的页"）。
**但这条路是堵死的**：007 的 FR-008 要求提示能让用户**判断下一步动作**，而两种原因的下一步
**完全不同**（见上表）。一条消息服务不了两种下一步；要区分就得知道哪些页是哪种原因，
那就是**第二个维度**——也就是 007 的 FR-011 明确禁止的那个"通用警告框架的 code 字段"。

⭐ 这件事本身是 FR-011 那条约束的**验证**：它在一天之内就拦下了一个真实的搭便车请求，
并且把它逼成了一次真正的设计讨论，而不是"加个枚举值"。

### 顺带解决的同类问题

007 报告 §6.2：被 reconciliation 恢复的文档拿不到**任何**提示——它接手的是一份卡在发布中的
文档，没有重新解析过文件，因此不知道有没有缺页，只能写空。这与本功能是**同一个设计问题**
（"提示怎么熬过处理过程中的交接"），分开做等于把同一个决策做两遍。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 解析失败的页也能被看见 (Priority: P1)

用户上传一份其中某些页面无法被解析的 PDF。文档正常入库、可检索，**同时**文档列表上有一条提示，
说明哪些页没能读进去，以及可以怎么办。

**Why this priority**: 这是本功能存在的全部理由，也是 007 留下的那半个洞。

**Independent Test**: 上传一份含无法解析页面的 PDF，断言文档列表上出现提示且指明页码。

**Acceptance Scenarios**:

1. **Given** 一份 PDF 有若干页无法被解析，**When** 处理完成，**Then** 文档状态为「就绪」且可正常检索
2. **Given** 上述文档，**When** 用户查看文档列表，**Then** 看到一条提示说明有页面未能读取
3. **Given** 上述提示，**When** 用户读它，**Then** 能判断出下一步动作（换工具重新导出，**而不是** OCR）
4. **Given** 一份所有页面都能解析的文档，**When** 处理完成，**Then** **不显示**这条提示

---

### User Story 2 - 两种缺失原因不会被混为一谈 (Priority: P1)

一份同时存在两种缺失的文档（有的页是扫描图、有的页解析失败），用户能分别看到两条信息，
**且两条给出的下一步动作不同**。

**Why this priority**: 与 US1 同级，因为它是本功能**不并进现有那一列**的全部理由。
如果两种原因最终仍被渲染成一句笼统的"有 N 页没进去"，那这一整期的设计成本就白付了——
还不如当初直接塞进去。

**Independent Test**: 构造一份两种缺失都有的 PDF，断言两条信息都出现且各自的建议动作不同。

**Acceptance Scenarios**:

1. **Given** 一份文档既有扫描页也有解析失败页，**When** 用户查看，**Then** 两类页码分别可见
2. **Given** 上述展示，**When** 用户读它，**Then** 两类各自的下一步动作是不同的、且都是具体的
3. **Given** 一份只有一种缺失的文档，**When** 用户查看，**Then** 只出现那一条，不出现空的另一条

---

### User Story 3 - 提示能熬过处理过程中的交接 (Priority: P2)

一份处理过程中被恢复流程接手完成的文档，其提示与"由原流程完成"时一致，不会因为换了谁完成而丢失。

**Why this priority**: 它修的是 007 报告 §6.2 记录的已知缺陷。优先级低于前两项，
因为恢复流程是少数路径；但它与前两项是同一个设计问题，分开做等于把决策做两遍。

**Independent Test**: 让一份有缺失的文档由恢复流程完成发布，断言提示仍然正确。

**Acceptance Scenarios**:

1. **Given** 一份有缺失页的文档在发布阶段被中断、由恢复流程完成，**When** 用户查看，**Then** 提示与正常完成时一致
2. **Given** 一份无缺失的文档走同样的恢复路径，**When** 用户查看，**Then** 没有提示

---

### Edge Cases

- **整份文档所有页都解析失败**：这属于**失败**（006 已实现的"无法解析该 PDF"错误），
  不是"成功但有提示"。本功能不得把它改判
- **同一页既解析失败又无文本层**：不可能——解析失败的页在统计文本层之前就已被跳过。
  但两类页码列表**必须互不重叠**，这一点要被断言
- **非 PDF 格式**：没有"页"概念，两类提示都恒为空
- **解析失败页数极多**：提示文案不得因为要列举页码而变得无法阅读
- **一份文档反复重新处理，两类缺失此消彼长**：每次处理必须整体覆盖两类，不得只更新一类
- **存量文档**：不追溯标记（沿用 007 的 FR-015）

## Requirements *(mandatory)*

### Functional Requirements

**承载与写入**

- **FR-001**: 系统 MUST 能够为一份处理成功的文档记录**哪些页面未能被解析**，与"无文本层的页面"分开记录
- **FR-002**: 两类记录 MUST 各自独立地出现和消失——一类有值不得强制另一类也有值
- **FR-003**: 两类页码列表 MUST 互不重叠
- **FR-004**: 每次处理成功时，两类记录 MUST **一并整体覆盖**；不得只更新其中一类而让另一类留下上次的值
- **FR-005**: 由恢复流程完成发布的文档，其两类记录 MUST 与由原流程完成时一致（修复 007 的已知缺陷）

**呈现**

- **FR-006**: 用户 MUST 能在文档列表看到两类提示，无需进入详情页或查阅日志
- **FR-007**: 两类提示给出的下一步动作 MUST 不同且具体——"无文本层"指向 OCR，"解析失败"指向换工具重新导出
- **FR-008**: 只存在一类缺失时，MUST NOT 出现另一类的空提示
- **FR-009**: 两类都不存在时，文档呈现 MUST 与本功能上线前**完全一致**
- **FR-010**: 提示 MUST 说明各类**分别有多少页**

**范围约束**

- **FR-011**: 本期 MUST NOT 把两类合并成一个通用的"警告列表"结构。第三种缺失原因出现时，
  MUST 再走一次独立的规格论证——**这条与 007 的 FR-011 是同一条纪律**
- **FR-012**: 本期 MUST NOT 实现 OCR、视觉检索，MUST NOT 尝试修复无法解析的页面
- **FR-013**: 全部页面都无法解析的文档 MUST 继续作为**失败**处理，MUST NOT 改判
- **FR-014**: 非 PDF 格式 MUST NOT 产生任何一类提示
- **FR-015**: 存量文档 MUST NOT 被追溯标记

### 需要在 `plan.md` 中解决的开放决策

- **D-001 · 承载形态**：第二列（与 `unextracted_pages` 对称）是显而易见的答案，但要论证清楚
  它不会滑向"每种原因一列"的无限增生——第三种原因出现时的判据是什么，要写下来。
- **D-002 · 提示怎么熬过发布交接**（FR-005）：恢复流程没有重新解析文件，因此它必须从**某处**
  读到这次处理算出的两类页码。落点候选：在进入发布阶段时就先落库、或让恢复流程重新解析。
  两者的代价不同，需要定死。
- **D-003 · 两条提示在一行里怎么排**：文档列表那一行已经有分片数和一条提示了，再加一条要么
  太挤要么被截断。需要定展示形态。

### Key Entities

- **解析失败页记录（Unparseable Page Record）**：一次处理中未能被解析、因而被跳过的页码。
  与"无文本层页记录"平行、独立、互不重叠，两者的**下一步动作不同**是它们必须分开的全部理由。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 上传一份含无法解析页面的文档后，用户**无需查阅日志**即可知道哪些页没进去——此项在改动前为失败
- **SC-002**: 用户看到提示后能说出下一步动作，且该动作**不是** OCR
- **SC-003**: 一份两种缺失都有的文档，用户能分别看到两类页码，且两条建议动作不同
- **SC-004**: 两类页码列表重叠率为 **0**
- **SC-005**: 由恢复流程完成的文档，其提示与由原流程完成时**完全一致**
- **SC-006**: 两类都不存在时，文档呈现与本功能上线前**逐字节一致**
- **SC-007**: 全部页面无法解析的文档仍作为失败呈现，错误文案与 006 上线时**完全一致**
- **SC-008**: 非 PDF 与未重新处理的存量文档，两类提示均为 **0** 条

## Assumptions

- **本功能不修复任何页面**，不让任何无法解析的页变得能解析。它只是把第二种已经发生的缺失说出来。
- **两类缺失的记录形态可以对称，但语义必须分开**——它们唯一的共同点是"这页没进去"，
  而用户拿它做的事完全不同。
- **失败路径完全不动**：006 的"无法解析该 PDF"（整份）与"没有文本层"（整份）两个错误一字不改。
- **提示仍然只在文档列表可见**，不进对话链路——沿用 007 的边界，本期不扩大。
- **不做通用化**：本期是第二种原因，不是第 N 种。FR-011 对第三种原因保留同样的门槛。
