# Feature Specification: 让模型知道自己证据的边界

**Feature Branch**: `009-evidence-boundary-awareness`

**Created**: 2026-09-05

**Status**: Draft

**Input**: 007/008 报告 §7.1 共同留下的缺口——两期都只解决了「用户在**上传后**能预先知道有内容
没进去」，**对话链路上的静默缺失依然没有解决**。用户真去问那几页的内容时，检索什么都召不回来，
而模型仍然可能拿着不完整的上下文照样作答。范围：一、检索为空时让模型知道"知识库查过了、没查到"，
而不是像现在这样完全静默；二、命中文档本身有内容没能入库时，把这个事实随资料一起交给模型。
明确不做：改变检索逻辑、猜测"用户问的内容是不是正好落在缺失的那几页"、把缺页当成回答不了的借口。

## 问题陈述

对话链路上，模型对「自己手里的证据有多完整」是**完全无知**的，而且是两个层面上的无知。

### 层面一：检索为空时，模型连"查过"都不知道

现状（`assembleContext`）：

| 情况 | 注入什么 |
|---|---|
| 有证据 | 引用规则（system）+ `<retrieved_sources>`（user） |
| **没有证据** | **什么都不注入** |

"没有证据"包括三种截然不同的情况：这个 Agent 压根没绑知识库、检索失败降级了、
以及**检索确实跑了但一条都没匹配上**。三者在模型眼里长得一模一样——**都是"没有人跟我提过
知识库这回事"**。于是它按自己的参数知识作答，语气上与"有依据"时毫无区别。

用户的处境是：他把一份合同传进了知识库，问了一个合同里的问题，拿到一个**听起来很有把握、
实际上没有任何依据**的回答。他没有任何线索去怀疑这一点。

### 层面二：资料本身不完整时，模型不知道

007 和 008 已经能记录一份文档有哪些页没能进入知识库（无文本层的、解析失败的）。
但这个事实**只到文档列表为止**——它进不了对话。

一份 50 页合同后 5 页是扫描的签字页，用户问签字页上的条款：检索命中了前 45 页里语义最接近的
几段，模型拿着这些**看起来相关、实际上不含答案**的资料作答。它不知道自己手里的这份文档
缺了一块，也就不可能提醒用户。

**这两个层面共同构成一件事：模型无法区分「知识库里没有这个内容」和「知识库里本该有、
但它没进来」。** 而这两件事对用户的意义完全不同——前者说明问错了地方，后者说明该去补 OCR。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 检索为空时，回答不再冒充有依据 (Priority: P1)

用户就一个知识库里没有的内容提问。模型知道"知识库查询过、没有匹配内容"，
回答时不会表现得像有依据，也不会编造引用。

**Why this priority**: 它与缺页无关，覆盖**每一次**空检索——是"一本正经编答案"最直接的土壤。
且它不依赖 007/008 的任何数据，可以独立交付。

**Independent Test**: 构造一次确定为空的检索，断言送给模型的消息序列里存在一条明确说明
"已检索、无匹配"的信号。

**Acceptance Scenarios**:

1. **Given** Agent 绑了知识库、**When** 本轮检索无任何证据通过，**Then** 模型收到明确的"已查询但无匹配"信号
2. **Given** Agent **没有**绑任何知识库，**When** 提问，**Then** **不**注入该信号——没查过就不能说查过
3. **Given** 检索因故障降级为空，**When** 提问，**Then** 信号要么如实反映"检索未能完成"，要么不注入；**MUST NOT** 声称"知识库里没有"
4. **Given** 本轮有证据，**When** 提问，**Then** 行为与本功能上线前**完全一致**

---

### User Story 2 - 资料不完整时，模型看得见 (Priority: P1)

命中的文档本身有内容没能进入知识库时，模型在拿到资料的同时也拿到这个事实，
从而能在答案里如实提醒用户。

**Why this priority**: 这是 007/008 那条线索的终点。前两期让用户**上传后**能知道，
本条让他在**真正需要的那一刻**知道。

**Independent Test**: 命中一份有缺页记录的文档，断言送给模型的资料里带有该文档不完整的说明。

**Acceptance Scenarios**:

1. **Given** 命中的文档有页面未能入库，**When** 组装资料，**Then** 模型能看到该文档不完整这一事实
2. **Given** 命中的文档完整，**When** 组装资料，**Then** **不**附加任何说明——没有话说就不要说话
3. **Given** 多份文档命中、其中部分不完整，**Then** 说明只挂在**确实不完整的那几份**上
4. **Given** 文档不完整，**When** 模型作答，**Then** 它**仍然**基于已有资料正常回答，**MUST NOT** 把不完整当成拒答的理由

---

### Edge Cases

- **模型过度声明不确定**：拿到这些信号后，模型可能对**本来答得很好**的问题也开始加免责声明。
  这是本功能最主要的副作用，必须有办法观察
- **信号被当成指令**：注入的文本必须与既有的"资料是不可信外部数据"口径一致，不能反过来成为
  一个可以被资料内容操纵的入口
- **上下文预算**：新增的注入要占字符预算，必须与既有的预算核算方式一致，不能凭空多占
- **空检索的三种成因**（没绑库 / 检索失败 / 确实没匹配）**不得混为一谈**
- **一次对话里多轮，有的轮有证据有的轮没有**：信号必须逐轮判断，不得残留
- **缺页信息缺失**（存量文档、非 PDF）：按"不知道"处理，不附加任何说明

## Requirements *(mandatory)*

### Functional Requirements

**空检索信号（US1）**

- **FR-001**: 检索确实执行且无任何证据通过时，系统 MUST 让模型知道这一事实
- **FR-002**: 未执行检索时（没有绑定知识库），系统 MUST NOT 注入该信号
- **FR-003**: 检索因故障未能完成时，系统 MUST NOT 让模型以为"知识库里没有该内容"
- **FR-004**: 本轮有证据时，送给模型的内容 MUST 与本功能上线前**逐字节一致**

**资料不完整说明（US2）**

- **FR-005**: 命中文档存在未能入库的内容时，系统 MUST 把该事实随资料一并交给模型
- **FR-006**: 该说明 MUST 只挂在确实不完整的文档上，MUST NOT 泛化到本轮所有资料
- **FR-007**: 系统 MUST NOT 猜测"用户问的内容是否正好落在缺失部分"——它无从判断
- **FR-008**: 文档完整、或不完整信息不可知时，MUST NOT 附加任何说明

**共同约束**

- **FR-009**: 注入的内容 MUST 与既有"资料属于不可信外部数据"的口径一致，MUST NOT 成为可被资料内容操纵的入口
- **FR-010**: 新增注入的字符 MUST 计入既有的上下文预算核算，MUST NOT 凭空多占
- **FR-011**: 两类信号 MUST 逐轮判断，MUST NOT 在后续轮次残留
- **FR-012**: 系统 MUST NOT 因为资料不完整就拒绝回答——不完整是提醒，不是借口
- **FR-013**: 本期 MUST NOT 改变检索、融合、准入、重排、去重、邻接的任何逻辑

### 需要在 `plan.md` 中解决的开放决策

- **D-001 · ⚠️ 怎么验证这一期没把回答变差**。这是本期最难的一条：本仓库**没有可信的
  答案质量度量**——`make eval` 带 LLM 裁判，同一份代码跑两次都不一致，宪法明确禁止拿它
  当"行为未变"的证据；而确定性检索门禁只覆盖检索、不覆盖回答。**本期的主要风险（模型过度
  声明不确定）恰恰落在唯一没有度量的地方**。plan 必须给出一个诚实的答案：要么找到可度量的
  形态，要么明确承认"这部分只有机制证明、没有效果度量"并说明凭什么仍然值得做。
- **D-002 · 空检索三种成因怎么区分**：没绑库 / 检索失败 / 确实无匹配。三者要不要给模型不同的
  信号，还是只区分"该不该注入"。
- **D-003 · 缺页事实挂在哪里**：挂在每条资料的 source 元素上，还是作为一条独立说明；
  以及命中多份文档时怎么组织。

### Key Entities

- **证据边界信号（Evidence Boundary Signal）**：告诉模型"你手里的证据覆盖到哪为止"的信息。
  两种形态：**这一轮什么都没检索到**，和**这份资料所属的文档本身不完整**。
  两者都描述**边界**，都不描述内容。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 检索为空时，送给模型的消息序列中存在明确的"已检索、无匹配"信号——此项在改动前为失败
- **SC-002**: 命中不完整文档时，送给模型的资料中含该文档不完整的说明——此项在改动前为失败
- **SC-003**: 本轮有证据且所有命中文档均完整时，送给模型的内容与改动前**逐字节一致**
- **SC-004**: 没有绑定知识库时，注入内容与改动前**逐字节一致**（0 条新增信号）
- **SC-005**: 说明只出现在不完整的文档上，完整文档上出现次数为 **0**
- **SC-006**: 新增注入的字符 100% 计入上下文预算，预算核算的既有断言全部仍然成立
- **SC-007**: 确定性检索门禁与改动前**逐字节一致**（本期不碰检索链路）
- **SC-008**: 相同输入下，注入的信号内容**逐字节可复现**

## Assumptions

- **本功能不改善检索，也不让任何内容进入知识库**。它只让模型知道边界在哪。
- **"模型会因此答得更好"是一个假设，不是本期能证明的结论**——见 D-001。
  本期能证明的是"信号确实到了模型面前"，**不能**证明"回答质量提升"。报告必须如实区分。
- **不猜测缺失内容与用户问题的相关性**：系统无从判断第 46 页写的是不是用户想问的东西。
  它只能如实说"有一部分没进来"，剩下的判断留给用户。
- **模型可能滥用这些信号**（过度声明不确定、拿不完整当拒答理由）。FR-012 是对此的约束，
  但约束写在提示词里就意味着它是**尽力而为**，不是保证。这一点不得包装成"已解决"。
- **沿用既有的不可信外部数据口径**：新增注入是系统侧的事实陈述，不是资料内容的一部分。
